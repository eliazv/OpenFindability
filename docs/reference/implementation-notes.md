# Implementation notes

Detailed, per-topic notes on how each part of OpenFindability works and why: API quirks, storage shapes, dedupe keys, known limitations. `AGENTS.md` holds the short rules; this file holds the depth. Read the section for the area you are about to change, and add to it (under the matching heading) when you ship a feature there.

## Storage (SQLite, Drizzle, store API)

- `project:update` uses `updateProjectWith`/`updateProject` to update only one projects row under an immediate transaction, incrementing the store revision atomically. It does not load metric/raw JSON tables or replace child rows, avoiding heap exhaustion on large stores. Immutable identity/timestamps are protected; the existing full-snapshot stale-write guard detects these targeted edits. Release lookups/logging likewise use the bounded projects query and connector-run append helpers.

- Startup migrations retain Drizzle's files, timestamps, hashes and journal table but run through `migrateSqlite` inside one `BEGIN IMMEDIATE` transaction. The writer lock is acquired before reading the last applied migration, preventing two CLI/UI/test processes from applying the same ALTER concurrently. Busy timeout is set before setup; failed initialization closes the native handle. Tests cover concurrent connections and rollback/retry without real project data.

- Runtime is Node 24 (`.node-version`, package engines); pnpm explicitly allows the `better-sqlite3` build script through `onlyBuiltDependencies`. A copied/stale Node 22 native binary fails with ABI 127 vs 137; `pnpm rebuild better-sqlite3` installs the matching binary without touching the database. The backup command uses SQLite's online backup plus integrity verification and must succeed before pending migrations are opened. Build/cache download permissions are separate from SQLite data access.

- Changed warehouse partitions are staged, then merged by stable ID and reconciled by row count in the same per-table transaction. Only obsolete IDs are deleted. Manifest rows use an upsert. This avoids DuckDB indexed delete/reinsert conflicts on large vectorized partitions while preserving unique ID constraints, idempotency, removals and atomic publication. Regression coverage includes a partition above two vectors (4,100 rows), modified existing IDs and new rows.

- Warehouse schema v2 adds explicit GA4 `sessions`/`key_events`, populated by the connector and recoverable from existing validated JSON values via `repair:analytics` (dry-run unless `--apply`). Cloud migration is additive and recorded in `warehouse_schema_migrations`; partition insertions name their columns to survive physical-column order changes. Stable IDs receive unique indexes; staging preflight rejects missing/duplicate IDs and dangling non-null project references. Cloud FK dependencies are intentionally not introduced across independently replaced tables.
- `warehouse-semantics.ts` publishes sanitized per-project/source configuration booleans and long-format daily/latest KPI views, source coverage/freshness, monthly GSC aggregates, latest index audits, daily crawler summaries and App Store quality flags. Currency, source, unit and grain remain dimensions; RevenueCat gauges/rolling revenue never enter daily KPIs. Known inflated iOS history remains original but `trusted_downloads=NULL` prevents its inclusion in daily KPIs. Comments are synchronized only when changed; `docs/guide/warehouse-ai-guide.md` is the maintainable agent-guide text.
- GSC index links are reconciled by `gsc-project-links.ts`: explicit unique normalized property mapping first, conservative exact-domain fallback for projects without a GSC property second. Ambiguous/mismatched mappings remain unassigned. Existing assignments/raw responses are preserved; sync/audit repair previously unassigned inspections and run metadata. `repair:analytics` applies this repair without API calls and normalizes legacy `ecommerce` project types to `web`, preserving category information.

- SEO/GEO observations use `seo_geo_observations` with provider, kind, stable SHA-256 identity, scope, explicit window/grain, normalized metric JSON, coverage, raw provider row and fetched timestamp. They are part of the store snapshot and project-replacement transaction so metadata edits preserve their FK children. Bing daily totals additionally feed `metric_snapshots`; Bing details do not enter GSC-only tables. New project fields map exact Bing site URL, Cloudflare zone, optional Clarity project ID and the environment variable NAME for its project-scoped token.
- `lib/integrations/motherduck.ts` exports a selective warehouse from a WAL-consistent SQLite online backup. The source snapshot is read in bounded chunks; local SHA-256 partitions by project/month detect changes and removals. A local DuckDB staging table feeds atomic per-table remote replacement and manifest updates, with row-count reconciliation. Subsequent runs resume already committed partitions; source tables can differ in freshness after a failure, surfaced by `warehouse_runs`. Scanning/hashing is full local work; only transfer is incremental. `warehouse_metadata` protects unmanaged destinations and records schema version 1. No credential fields or raw API payloads are exported; project and run fields use explicit allowlists. GSC detail selection requires the daily grain marker. AdMob/revenuecat/Clarity views and `metric_dictionary` preserve metric semantics. `scripts/sync-warehouse.ts` is dry-run by default; remote writes require `--apply`, and completed/failed apply attempts log `connector_runs.source=motherduck`. Driver errors are redacted before CLI output. Guide: `docs/guide/seo-geo-warehouse.md`.

## Bing, Cloudflare and Clarity

- Warehouse source projection is materialized one table at a time into indexed SQLite temporary memory tables. Only the selected analytical columns are materialized; large raw JSON is parsed once for GSC daily-grain filtering, rather than re-scanned for every monthly partition. Rows are then appended to DuckDB in bounded chunks. `--verify-local` exercises the same transfer and view creation against in-memory DuckDB without a token or any network calls. Temporary backup DB, WAL/SHM sidecars and directory are removed when the operation finishes.

- `discover-seo-geo.ts` discovers verified Bing REST sites and paged Cloudflare zones; Clarity's Data Export has no project inventory endpoint, so the global project token is mapped only if URL host evidence matches a single local website. It saves local mapping only with `--apply`; unmapped properties are reported rather than guessed from app names. Multi-project Clarity uses distinct token env names. Secrets stay in `.env`.
- The three connectors participate in manual `syncProjects`, with per-project errors isolated and every result logged. Bing REST uses JSON endpoints with key in the request query; errors intentionally omit URLs/bodies. Provider dates decode Microsoft's signed reporting offset. Query/page detail dates retain `provider_period` grain because the connector does not infer daily coverage. Failed detail endpoints produce partial imports while daily successes survive. Empty results are `no_data` rather than invented zeros.
- Cloudflare requests adaptive groups for 23 completed UTC hours with user-agent AI crawler filters, recording sampling interval, URL path, host and HTTP status. Rows are scoped to the project's website host (including www variant). Successful non-truncated windows replace the old crawler groups in their covered hours; truncated 10k results are partial and do not erase existing groups. A separate coverage row records even an empty window. The Free retention window limits recovery; user agents can be spoofed. These are sampled proxy requests, never evidence of citations.
- Clarity requests `numOfDays=1&dimension1=URL` once per project/sync, preserving provider metric names/fields and matching only the configured host. The API's rolling 24h window is approximated from request start; overlapping snapshots must never be summed. Quotas: 10 calls/project/day, max 1000 rows, no pagination, no arbitrary historical range. No replay/session identifiers are fetched. `clarity_latest` selects only each project's latest export as a whole so vanished URLs do not reappear from old windows.
- `seoGeoSnapshot`/`seoGeoMarkdown` provide cached source-separated summaries with coverage and bounded sample rows; exposed through CLI dated reports and the read-only MCP tool `get_seo_geo_snapshot`. No composite GEO score is calculated.

- Data lives in `data/openfindability.db`, a local SQLite database accessed through Drizzle ORM (`better-sqlite3` driver). WAL journal mode and `foreign_keys = ON` are set at connection time in `lib/db/client.ts`.
- `lib/sync.ts` dedupes on every sync run instead of just appending: `upsertByKey`/`upsertSnapshots`/`upsertQueries`/`upsertPages` replace any existing row sharing the same key (`metricSnapshots`: `projectId::source::date`; `searchQueries`: `projectId::date::query::page`; `pageMetrics`: `projectId::date::page`) with the newly synced one before writing. This makes re-running `pnpm run sync` the same day idempotent instead of piling up duplicate rows that would double-count in reports/insights/charts. Play Console's `appReviews` keeps its own existing `reviewId` dedupe; ASO's `appKeywords` is intentionally left append-only (opt-in, cached upstream).
- Storage moved from a single hand-rolled JSON file to SQLite (via `better-sqlite3` + `drizzle-orm`/`drizzle-kit`), to make the data properly relational/queryable while keeping v0.1 simple (no server process, no extra infra — still a single local file). `lib/db/schema.ts` defines one `sqliteTable` per `AppData` array (same 10 tables/shapes as `lib/types.ts`), with `FOREIGN KEY ... ON DELETE CASCADE` from every project-scoped table to `projects`, plus the same unique/non-unique indexes the old code relied on for dedup keys (e.g. `metric_snapshots_project_source_date`, `search_queries_project_date_query_page`). `lib/db/client.ts` opens `data/openfindability.db`, sets the WAL + foreign-key pragmas, and runs `migrate()` against `./drizzle` at module load — so importing the store still requires zero manual setup, same as the old JSON file. `drizzle.config.ts` (`dialect: "sqlite"`) is `drizzle-kit`'s config for generating migrations from `lib/db/schema.ts`; the generated SQL under `drizzle/` is committed to git (it's schema history, not runtime data), unlike `data/*.db*` which stays gitignored (`.db`, `.db-wal`, `.db-shm`, `.db-journal`).
- `lib/store.ts`'s public API is unchanged on purpose (`readData(): Promise<AppData>`, `writeData(data): Promise<void>`, `updateData(mutator)`, `getDataFilePath()` — now re-exporting `lib/db/client.ts`'s `getDbFilePath`), so every consumer (`lib/insights.ts`, `lib/report.ts`, `lib/doctor.ts`, `lib/sync.ts`, `app/*.tsx`, every `scripts/*.ts`) needed zero changes. Internally: `readData()` runs one `db.select().from(table).all()` per table and normalizes SQL `NULL` back to `undefined` (Drizzle always decodes `NULL` as `null`, but `AppData`'s optional fields are typed `T | undefined`) — except `AppKeywordMetric.appRank`/`AsoAppRankSnapshot.appRank`, which keep a literal `null` since those fields are explicitly nullable, not just optional. `writeData(data)` wipes every table and bulk-reinserts the full `AppData` object in one `db.transaction(...)` (chunked ~50 rows per insert to stay under SQLite's bound-parameter limit) — this is semantically identical to the old "overwrite the whole JSON file" behavior because every caller (`lib/sync.ts`, `scripts/seed-demo.ts`, etc.) already builds the complete `AppData` in memory and calls `writeData()` exactly once at the end. `AppReview.text` is stored under the DB column/property `reviewText` (the JS name `text` would collide with Drizzle's `text()` column-builder import) and is the one field renamed back and forth in `lib/store.ts`.
- `scripts/migrate-json-to-sqlite.ts` is a one-time helper: reads the legacy `data/openfindability.json` and calls `writeData()` to import it into SQLite. Run once via `pnpm run db:migrate-json`, then the legacy `.json` file can be deleted. `next.config.ts` sets `serverExternalPackages: ["better-sqlite3"]` so Turbopack/webpack doesn't try to bundle the native addon for the server build. `pnpm run db:studio` launches Drizzle Studio, a free local GUI SQL browser against `data/openfindability.db` — the most direct way to make the data "well-queryable" ad hoc, on top of the existing CLI scripts/reports. `pnpm run db:generate` regenerates `drizzle/*.sql` after editing `lib/db/schema.ts`.
- This pass is storage-layer only: `lib/insights.ts`/`lib/report.ts` still aggregate in plain JS over the full `AppData` blob returned by `readData()`, not via SQL `GROUP BY`/`SUM`. That stays a valid future optimization but wasn't needed for `readData()`/`writeData()` to keep their exact same signatures and 100% backward compatibility.
- `lib/db/client.ts` exports `createDb(dbFilePath, migrationsFolder): AppDb` (factory) alongside the module-scope singleton `db`; `lib/store.ts` exports `readDataWith(database)`/`writeDataWith(database, data)` (the same logic `readData`/`writeData` use internally, parameterized by db instance) alongside the `db`-singleton-bound `readData`/`writeData`. This exists for `mcp/server.ts`, which runs via `tsx` from an arbitrary cwd in other repos (see `docs/guide/mcp-server.md`) and therefore can't rely on `process.cwd()`-based path resolution like the main app and CLI scripts do — it resolves its own `data/openfindability.db`/`drizzle/` paths from `import.meta.url` instead, builds its own `AppDb` via `createDb`, and its `readProjects`/`readStoredData`/`writeStoredData` helpers are thin wrappers around `readDataWith`/`writeDataWith` against that instance.
- Known pre-existing limitation (not introduced by the SQLite migration): `mcp/server.ts`'s `@/lib/...` path-aliased imports only resolve correctly via `tsx` when the process's cwd is the OpenFindability repo itself; invoking it with `tsx /path/to/OpenFindability/mcp/server.ts` from a different repo's cwd (the documented "use from any project" flow in `docs/guide/mcp-server.md`) fails to resolve `@/` imports regardless of storage layer. Fixing this (e.g. switching `mcp/server.ts` to relative imports) is a separate, currently unscheduled fix.
- `pnpm run db:generate` was re-run after these schema changes (`drizzle/0002_damp_karen_page.sql`) — always regenerate + apply (`readData()`/`writeData()` auto-run `migrate()` at module load, so just re-running any script does it) after editing `lib/db/schema.ts`.
- Commands: `pnpm run test:gsc` tests daily/legacy isolation, weighted aggregates, pagination and row-cap fallback. `pnpm run db:backup` takes a WAL-consistent snapshot and verifies `integrity_check` in ignored `data/backups/`. Tests were added for local runs; no CI actions or live Google API calls required.
- Remaining architecture concern: `writeDataWith` rewrites all app tables in a single transaction on each sync; atomic but can be slow as detailed historical GSC data grows, and independent writers can race if using separate processes. Prefer a future incremental, per-project SQLite write path before very large multi-year query-level backfills. Do not conflate with this fixed daily-grain bug.

## Google Search Console

- GSC backfill defaults to 30 days.
- GSC sync also pulls device/country/searchAppearance breakdowns (aggregated over the whole synced range, not daily) into `gscDimensionBreakdowns`, plus sitemap status (`sitemaps.list`) into `gscSitemaps`. The GSC report (`buildGscReportMarkdown`) renders these as extra sections when present.
- Manual GSC index auditing is implemented by `pnpm run audit:index [max-urls-per-site] [slug-or-property-filter]` (`scripts/gsc-index-audit.ts` + `lib/gsc-index-audit.ts`). It lists every GSC property visible to the service account (including properties not mapped to an OpenFindability project), discovers URLs from submitted sitemap XML, 90-day Search Analytics pages, stored GSC rows and audit history, and calls URL Inspection with a default/maximum budget of 2,000 URLs per property/day. Same-day rows are skipped; never-inspected URLs come first, then existing high/medium problems and older successes, so large properties make progressive coverage rather than exhausting every new day's quota on the same issues. Results and raw API payloads live in `gscIndexInspections` (`projectId` nullable, `siteUrl` always present); `connectorRuns.source` accepts `gsc_index`. Reports are written globally to ignored `private-notes/index-audits/` and to `project/<slug>/reports/`; unmapped properties derive the slug from their domain (for example VitaRomagna writes to `project/vitaromagna/reports/`). `pnpm run report -- <slug> index` regenerates reports for configured projects. The dashboard shows latest-state totals/problems globally and per project. This is the broadest public-API audit possible, not Google's unavailable bulk Page Indexing inventory.
- The index audit runs 16 URL Inspection calls concurrently (well below the official 600 QPM/property quota at observed API latency) and checkpoints the full store every 500 completed inspections so a late failure does not discard a large in-memory batch. Project reports also surface each stored sitemap's submitted/indexed counts from its preserved raw GSC payload.
- The GSC report includes a Trend section (mirrors the ASO one) comparing page-level metrics between the two most recent `pageMetrics` snapshot dates per project (clicks/impressions/avg position delta), shown only when at least two dates exist. `formatDelta` (`lib/report.ts`) takes an optional `decimals` option so position deltas round to 1 decimal instead of showing long floats; ASO's integer scores are unaffected (default `decimals: 0`).
- `syncGscProject` now preserves the **true day** on `searchQueries` and `pageMetrics`; it uses 7-day windows with paged GSC requests, falls back to day-level requests on 50k row cap, and validates API date/page/query keys before any caller persists data. GSC always exposes top query rows rather than exhaustive raw search logs. Use `{ details: false }` for totals-only comparisons (e.g. MCP compare_periods).
- Valid daily-detail rows are marked under `rawJson._openfindability` with version 2 and grain `day`. Pre-existing `date=endDate` 30-day query/page aggregates remain untouched in SQLite but are excluded by `lib/gsc-detail.ts` from GSC trends, top pages/queries, and 28-day opportunities. They cannot be transformed into accurate daily rows retroactively; re-sync GSC with real date dimensions to rebuild those windows.
- GSC report and project top URLs/queries use the last 28 days aligned to the latest GSC snapshot; impressions-weighted averages are used for positions. MCP live queries/URL ranking now aggregate new daily details before returning ranked items and compare equal finalized windows (ending D-2).
- On each successful GSC sync, replace prior v2 daily page/query rows for every covered finalized day (including rows Google stopped returning), while retaining unmarked legacy history. Recomputed opportunities preserve prior ignored/done status and stable ID when semantic identity matches.

## Monetization (RevenueCat, AdMob)

- RevenueCat and AdMob connectors (`lib/connectors/revenuecat.ts`, `lib/connectors/admob.ts`) are third-party API connectors, not SaaS-specific code — they follow the same pattern as GSC/Umami/Play Console; see `docs/guide/monetization-workflow.md`.
- Configure `revenueCatProjectId`/`admobAppId` per project when needed.
- RevenueCat auth is a V2 secret key (Bearer token), not OAuth. Each RevenueCat project has its own key, so `Project.revenueCatApiKey` (added 2026-08-21) lets every app sync in one `pnpm run sync` run instead of requiring the single global `REVENUECAT_API_KEY` env var to be swapped by hand between apps — `syncRevenueCatProject` (`lib/connectors/revenuecat.ts`) uses `project.revenueCatApiKey || process.env.REVENUECAT_API_KEY`, so the env var still works as a fallback for projects with no key of their own. Set it via `pnpm run project:update -- --slug <slug> --revenuecat-api-key sk_xxx`. The RevenueCat overview metrics endpoint is point-in-time (no date-range param), so this connector only ever writes one snapshot per sync run for the current date — historical MRR trend only builds up from running `pnpm run sync` regularly, there is no backfill.
- AdMob auth is interactive OAuth2 (`ADMOB_CLIENT_ID`/`ADMOB_CLIENT_SECRET`/`ADMOB_REFRESH_TOKEN`/`ADMOB_PUBLISHER_ID`); mint the refresh token once via `pnpm run admob:auth` run on your own machine (needs a real browser).
- RevenueCat's `revenue` snapshot field (`revenue_last_28_days`) is a rolling window, not a true daily total — never sum it across dates, only use the latest snapshot per project. AdMob's `revenue` snapshot field is a true daily total and is safe to sum across dates/projects.
- RevenueCat/AdMob sync as part of default `pnpm run sync` (like gsc/umami/play_console); ASO stays opt-in only (`pnpm run sync:aso`).
- `pnpm run report -- <slug> monetization` (or `all`) writes a dated `project/<slug>/reports/<date>-monetization-data.md` via `buildMonetizationReportMarkdown` in `lib/report.ts`: AdMob revenue (that day/this month/previous month, true daily sums) and RevenueCat (latest MRR/active subscribers/trials/new customers, rolling 28-day revenue) plus a per-source daily/MRR trend table (last 30 rows). Skipped with a log message if the project has neither `admobAppId` nor `revenueCatProjectId` configured.
- AdMob apps that ship on both stores have two AdMob app ids (Android + iOS); `Project.admobAppIdIos` was added alongside the existing `Project.admobAppId` (which stays Android/primary) so one OpenFindability project can represent one logical app. `syncAdmobProject` (`lib/connectors/admob.ts`) filters the network report to whichever ids are set (`dimensionFilters: [{ dimension: "APP", matchesAny: { values: appIds } }]`) and sums matching rows into a single `metricSnapshots` row per project per day, instead of matching only one hardcoded app id.
- AdMob mediation report data (per ad-source/format breakdown — AdMob Network, AppLovin, Unity Ads, Meta, etc. — with ad requests, match rate, impressions, clicks, estimated earnings, observed eCPM) is synced into a new table/type, `admobMediationMetrics`/`AdmobMediationMetric` (`lib/types.ts`, `lib/db/schema.ts`), not into `metricSnapshots` (different shape/grain — one row per project+date+adSource+format, not one row per project+date). `syncAdmobProject` returns `{ result, snapshots, mediationMetrics }`; `lib/sync.ts` upserts `admobMediationMetrics` keyed on `(projectId, date, adSourceId, format)`. `getAdmobRevenueRows` in `lib/insights.ts` now uses mediation earnings as the complete business total (AdMob Network + third-party winners) and falls back to the network report for legacy days only; dashboard charts/summaries and `buildMonetizationReportMarkdown` use that same source and the report includes a source/format breakdown plus reconciliation.
- `scripts/add-project.ts` accepts `--admob-app-id-ios` alongside the existing `--admob-app-id`.
- `pnpm run admob:apps` (`scripts/admob-list-apps.ts`) lists every app registered under the AdMob account (`accounts.apps.list`) with its `ca-app-pub-...~...` id, platform and display name — the fastest way to find app ids to configure per project instead of digging through the AdMob UI.
- `syncAdmobProject(project, startDate, endDate)` takes a date range, not a single day: both the network report and the mediation report use the `DATE` dimension so one API call returns one row per day (per app/ad-source/format) for the whole range, which we then group by day in `lib/connectors/admob.ts` into one `metricSnapshots`/`admobMediationMetrics` row per date. `lib/sync.ts` calls it with `daysAgo(backfillDays)` to `daysAgo(1)`, reusing the same `backfillDays` option (default 30) already shared with GSC/Play Console. `scripts/sync.ts` accepts an optional extra CLI arg to override it for a one-time deep backfill; `pnpm run sync:admob:backfill` is a fixed 1500-day (~4y) version of this baked into `package.json` (pnpm's `--` arg passthrough for custom values mis-quotes on Windows/PowerShell — use `npx tsx scripts/sync.ts admob <days>` directly instead). AdMob simply returns fewer rows than requested once it runs out of real history — asking for more days than the account/app has data for is harmless.

## AdSense

- **AdSense connector** (`lib/connectors/adsense.ts`, source `"adsense"`) — for site display-ad revenue, separate from AdMob (app ads). AdSense Management API v2 has no OAuth-free service-account option either: same interactive OAuth2 pattern as AdMob (`ADSENSE_CLIENT_ID`/`ADSENSE_CLIENT_SECRET`/`ADSENSE_REFRESH_TOKEN`, minted once via `pnpm run adsense:auth`, needs a real browser) plus `ADSENSE_ACCOUNT_ID` (bare `pub-...` id, discoverable via `pnpm run adsense:accounts` → `accounts.list()`; the connector prefixes it to `accounts/${id}` itself, mirroring how `ADMOB_PUBLISHER_ID` is stored bare and prefixed in `lib/connectors/admob.ts`). Enable **"AdSense Management API"** (`adsense.googleapis.com`) in Cloud Console — not "AdSense Platform API" (`adsenseplatform.googleapis.com`), which is for reseller/multi-account platforms, the wrong product for reading your own account's data.
- A project maps to AdSense via `Project.adsenseSiteDomain` (a domain string like `example.com`), not an app id — AdSense reports on websites, not apps. `syncAdsenseProject(project, startDate, endDate)` calls `accounts.reports.generate` with a `DATE` dimension (same range-in-one-call pattern as AdMob) filtered by `OWNED_SITE_DOMAIN_NAME==<domain>`, and maps `ESTIMATED_EARNINGS`/`PAGE_VIEWS`/`IMPRESSIONS`/`CLICKS`/`AD_REQUESTS` into the existing `metricSnapshots` shape (`pageviews` reused the same way Umami uses it) — no new table needed, unlike AdMob's separate mediation table. AdSense's response shape is GET-style query params + a `{headers, rows}` result (dimension/metric name → column index), not AdMob's POST body + streamed `[{header},{row},...,{footer}]` — the two connectors share the pattern (OAuth2, date-range backfill, `Project` field → filter) but not request/response code.
- `pnpm run sync:adsense`/`pnpm run sync:adsense:backfill` mirror the AdMob commands exactly (same `backfillDays` default, same 1500-day fixed backfill script). `adsense` was added to `SourceType` (`lib/types.ts`), the `metric_snapshots.source`/`connector_runs.source` enums (`lib/db/schema.ts`), `scripts/sync.ts`'s `validSources`, and `lib/doctor.ts`'s credential/staleness checks.

## App Store Connect (copy, PPO experiments)

- ASC JSON requests are limited to the official HTTPS `/v1/` API, including pagination links, with a 30-second deadline. Network-denied (`EACCES`/`EPERM`), DNS, timeout, TLS, 401 and 403 errors are distinguished without exposing keys, query parameters or raw error bodies. No request is automatically retried because the connector also writes metadata. List pagination rejects repeated links and malformed resource arrays. A sandbox network denial is not evidence of invalid Apple credentials: repeat the authorized read outside the restricted sandbox.

- **App Store Connect API connector** (`lib/connectors/appstoreconnect.ts`) reads/writes live App Store product text and manages Product Page Optimization (PPO) tests; full workflow in `docs/guide/appstoreconnect-workflow.md`. Auth: ES256 JWT built with `node:crypto` only (`createSign("sha256").sign({ key, dsaEncoding: "ieee-p1363" })` gives the raw JOSE r‖s signature directly, so no `jsonwebtoken` dependency was added), from `ASC_ISSUER_ID`/`ASC_KEY_ID`/`ASC_PRIVATE_KEY_PATH` — the `.p8` key lives under `secrets/appstoreconnect/` (mirrors `secrets/google/`). No new `Project` field: it reuses the existing `appStoreTrackId` as the App Store Connect app resource id (Apple's ASC `id` for an app *is* the same numeric "Apple ID"). `pnpm run asc:apps` lists apps visible to the key to confirm the mapping.
- **Apple's PPO A/B-tests app icon/screenshots/app previews only — never text** (name/subtitle/description/keywords). This is a hard Apple platform limitation, not a gap in this connector. Text changes are therefore a read/write-with-history workflow, not a live split test: `pnpm run aso:pull-copy -- --slug <slug>` reads current App Info (name/subtitle) + the current editable App Store version's localization (keywords/description/promotionalText/whatsNew) and stores an append-only `ascMetadataSnapshots` row (`kind: "pull"`) per locale, plus a `project/<slug>/reports/<date>-appstoreconnect-copy.md` dump. `pnpm run aso:push-copy -- --slug <slug> --locale it [fields...] [--apply]` is dry-run by default (prints old→new diff, writes nothing) — only `--apply` PATCHes App Store Connect and stores a `kind: "push"` snapshot; version-scoped fields require an editable version (`PREPARE_FOR_SUBMISSION`/rejected state) to already exist, since writes never touch a live version.
- PPO experiments/treatments sync into two new tables, `ascExperiments`/`ascExperimentTreatments` (`lib/types.ts`, `lib/db/schema.ts`; `ascExperimentTreatments.experimentId` FKs to the *local* `ascExperiments.id`, not Apple's id), via `pnpm run asc:experiments -- --slug <slug>` (full project resync, list-then-replace like a lightweight version of `lib/sync.ts`'s upsert pattern). The same command's `--create-experiment "name" --element screenshot|appPreview|appIcon` and `--add-treatment <ascExperimentId> --name "..."` flags create real experiment/treatment shells via the API — but attaching the actual icon/screenshot/app-preview creative assets to a treatment is still a manual App Store Connect UI step (no asset-upload pipeline was built), and Apple exposes no results/conversion-metrics endpoint at all — winners are ASC-UI-only, so `buildAscReportMarkdown` states/treatments only, never fabricates a "winner".
- `connectorRuns.source` gained `"asc_metadata"`/`"asc_experiments"`; neither runs as part of default `pnpm run sync` — like ASO, this is an on-demand editorial workflow, not a daily metric pull. `pnpm run report -- <slug> asc` renders `buildAscReportMarkdown` (`lib/report.ts`) from whatever has already been pulled/synced above.
- `getAppInfoLocalizations` (`lib/connectors/appstoreconnect.ts`) now picks the *editable* `appInfo` resource (state in `EDITABLE_VERSION_STATES`) instead of just the first one Apple returns. Fixed 2026-08-13: an app with a version in progress has two `appInfo` resources (one live `READY_FOR_SALE`, read-only; one `PREPARE_FOR_SUBMISSION`, editable), and "first in the list" isn't reliably the editable one — the old code's writes intermittently 409'd with "can not be modified in the current state" against the live one.

## Play Console listing writes

- **Play Console listing write connector** (added 2026-08-17, `lib/connectors/play-console.ts`): `getPlayStoreListing(packageName, language)` / `updatePlayStoreListing(packageName, listing)` use the Android Publisher `edits` API (`edits.insert` → `edits.listings.get`/`.update` → `.commit`), reusing the same `GOOGLE_SERVICE_ACCOUNT_JSON`/`_FILE` + `androidpublisher` scope already used for review sync — no new credential needed, only a Play Console permission grant on that service account (Play Console → Users and permissions → app-level access → "Edit store listing" or similar; not configurable from here, verify in the Play Console UI if a project's push 403s). Language must be a full Play Store locale code (`it-IT`, not bare `it` — bare codes 400 with "requested language is not currently supported"). `pnpm run play:pull-copy -- --slug <slug> --language it-IT` reads the live title/shortDescription/fullDescription (no local snapshot table yet, prints only — unlike `aso:pull-copy` there's no `ascMetadataSnapshots`-equivalent history for Play Store pulls/pushes). `pnpm run play:push-copy -- --slug <slug> --language it-IT [--title/--short-description/--full-description[-file]] [--apply]` is dry-run by default like `aso:push-copy`; unlike App Store, there's no draft/editable-version precondition — `--apply` commits immediately and Google publishes within hours, no human review. Requires `Project.playConsolePackageName` to be set (`pnpm run project:update -- --slug <slug> --play-console <package.name>`); this field previously only gated the read-only reviews/ratings sync, now it also gates listing writes for the same project.

## App growth stats (Play vitals, Play install stats, App Store analytics)

- Play exports keep device (`installs`, `uninstalls`), user (`userInstalls`, `userUninstalls`) and event (`installEvents`, `uninstallEvents`) series separate. `readPlayInstallMetrics` shares parsing with preview-first `repair:play-metrics`, which fills only NULL new columns from validated raw CSV strings, preserves raw JSON/device values, and increments the store revision transactionally. Missing columns are unknown. Warehouse schema v4 adds these columns and `play_install_quality` highlights zero device uninstalls alongside positive user/event activity without relabeling metrics or inferring retention.

- The App Store connector no longer interprets a sessions/engagement report as a retention import. D1/D7/D28 remain missing until a validated report/cohort/unit parser exists; availability notes explain this rather than claiming successful retention. App Store quality views expose missingness and known pre-2025-09-21 download inflation explicitly. Downloads via Sales Reports remain independent and usable.

- **Account-wide app growth stats** (installs/uninstalls, crash/ANR rate, App Store downloads/retention), added 2026-08-21. `pnpm run discover:apps` (`scripts/discover-apps.ts`) lists every app visible to the configured Play Console/App Store Connect credentials and auto-creates/links `Project` rows (matched by `playConsolePackageName`/`appStoreTrackId`; never overwrites an existing project's other fields). `slugify` moved to a shared `lib/slug.ts` (both `scripts/add-project.ts` and `scripts/discover-apps.ts` import it now, instead of duplicating it). Three new connectors, three new sources (`play_vitals`, `play_stats`, `asc_analytics`), all part of default `pnpm run sync`, each upserted keyed on `(projectId, date)`:
  - `lib/connectors/play-vitals.ts` — Play Developer Reporting API (`playdeveloperreporting.googleapis.com`, v1beta1), reusing the same `GOOGLE_SERVICE_ACCOUNT_JSON`/`_FILE` service account with an added `playdeveloperreporting` OAuth scope (separate `GoogleAuth` instance from `play-console.ts`'s `androidpublisher`-scoped one — one service account, two scoped clients). `apps:search` gives real account-wide app discovery (unlike `androidpublisher`, which has no list-all-apps endpoint). `vitals.crashrate.query`/`vitals.anrrate.query` (resource names `apps/{packageName}/crashRateMetricSet`/`anrRateMetricSet`) return `userPerceivedCrashRate`/`userPerceivedAnrRate` as one row per day → `playVitalsMetrics`.
  - `lib/connectors/play-gcs-stats.ts` — installs/uninstalls/active-device-installs are **not exposed by any Play REST API** at all (confirmed: Play Developer Reporting only covers vitals). They only exist as a monthly CSV (`stats/installs/installs_<package>_<yyyymm>_overview.csv`, historically UTF-16LE, sometimes gzip-wrapped) auto-exported to a Cloud Storage bucket once enabled in Play Console → Setup → Statistics export. Read via the `googleapis` `storage` v1 client (no new dependency — reuses the `googleapis` package already installed) with the same service account granted `devstorage.read_only` scope and "Storage Object Viewer" IAM on the bucket. Bucket name is account-specific (`pubsite_prod_<id>`-shaped) and not derivable, so it's a required env var, `GOOGLE_PLAY_STATS_BUCKET` → `playInstallStats`. Skips cleanly with `skipped(...)` if the bucket isn't configured or a given month's CSV doesn't exist yet, rather than failing the whole `pnpm run sync`.
  - `lib/connectors/appstoreconnect-analytics.ts` — downloads and retention come from **two different, independent Apple APIs**, since neither alone covers both:
    - **Downloads**: the older Sales Reports endpoint (`GET /v1/salesReports?filter[reportType]=SALES&filter[reportSubType]=SUMMARY&filter[frequency]=DAILY&filter[reportDate]=...&filter[vendorNumber]=...`, `Accept: application/a-gzip` — Apple 406s on `Accept: application/json`) — immediate, no request/wait step, up to 365 days of real history. Requires `ASC_VENDOR_NUMBER` (account-wide, found in App Store Connect → Payments and Financial Reports; not derivable from the API). One gzipped TSV per calendar day covers every app under the vendor, so `fetchSalesReportForDate` caches per-date results in a module-level `Map` shared across every project synced in the same process — a 30-project backfill still only fetches each day once. Rows are matched to a project via the TSV's "Apple Identifier" column (== `project.appStoreTrackId`) and summed as `downloads`, excluding rows whose "Product Type Identifier" starts with `IA` (in-app purchases, not installs). This mirrors a working implementation from another local project (`Progetti/Altro/applytics`, a Flutter app) rather than being derived from docs alone.
    - **Retention**: the newer Analytics Reports API. `ensureOngoingAnalyticsRequest` finds or creates an `ONGOING` `analyticsReportRequests` resource per app (the *first* request for a given app requires an Admin-role API key; subsequent reads only need Sales/Finance/Reports role on the same key) — wrapped in try/catch so a failure here only drops retention, never the downloads already fetched via Sales Reports. Lists `reports` under that request, takes the latest `instances` for the sessions/retention-named report, downloads `segments` — those return a **signed CDN URL to a gzipped TSV**, not a JSON:API resource, so this file does its own raw `fetch` + `node:zlib` gunzip for that hop instead of reusing `appstoreconnect.ts`'s `ascFetch`. Column matching is fuzzy header-name search (`findColumn`) since Apple's exact schema isn't guaranteed stable.
    - Both merge into one `ascAnalyticsMetrics` row per date (downloads, retentionDay1/7/28), `rawJson` always preserved. `pnpm run sync:asc-analytics:backfill` runs with a 365-day range (Apple's real history limit for daily SUMMARY sales reports) instead of the default 30.
  - `buildGrowthReportMarkdown` (`lib/report.ts`) renders all three; `pnpm run report -- <slug> growth` (or `all`) writes `project/<slug>/reports/<date>-growth-data.md`, skipped if the project has neither `playConsolePackageName` nor `appStoreTrackId` configured.
  - iOS crash/ANR data has **no public Apple API** at all (Xcode Organizer/MetricKit only) — not attempted, unlike Android where vitals covers it.
  - `doctor.ts` gained credential checks for the Play vitals scope and the `GOOGLE_PLAY_STATS_BUCKET` env var (ASC Analytics reuses the existing App Store Connect credential check); `getStaleProjects` gained `play_vitals`/`play_stats`/`asc_analytics` entries keyed the same way as the other per-project sources.
- ASC Sales Reports downloads (`fetchSalesReportForDate`) count only first-time downloads (product types `1`/`1F`/`1T`/`F1`); updates (`7*`), redownloads (`3*`) and IAP (`IA*`) are excluded (fixed 2026-09-21 — earlier syncs inflated totals 2-5x). Rows synced before that fix and older than the 365-day Apple window (before 2025-09-21) are still inflated and cannot be re-fetched daily; ignore them when summing all-time.

## iOS central release preparation

- The public runner template and iOS guides contain fictional identities only; owner-specific mappings, native inventories and handoff notes belong in ignored `private-notes/ios-release/` and `secrets/ios/`. Sanitizing current files does not rewrite prior Git history. One private runner repository can serve every app; Match can clone a separate `signing` branch of that same repository using `MATCH_GIT_BRANCH` and `clone_branch_directly`, with no per-app workflow. A direct Mac/SSH backend is not implemented.
- Both `flutter` and `capacitor` project configs are supported. Local `workingDirectory` maps repository subfolders without changing the SQLite schema. `--path` discovers standard Flutter/Capacitor native projects directly or one level under `apps/`, matches configured main bundle/framework and rejects ambiguity (or accepts `--slug` to disambiguate). It reads native files without executing app configuration/scripts. The remote source is still the configured repo plus explicit approved SHA, not local file contents.
- The Capacitor runner pins Node, uses `npm ci`, a configured npm web build script and `cap sync ios --deployment`, then Xcode archive/export; requested marketing/build versions are set in the temporary native targets after project build scripts run. Workspace/project/targets are configurable and validated as relative paths. Flutter keeps its existing builder, including nested working directories. Both use the same signing/IPA/ASC checks. Two-component numeric marketing versions are allowed. CocoaPods and lockfiles are required; flavor Flutter and SPM-only Capacitor need additional builders. Native validation per app remains outstanding until the macOS pilot.

- `ios-status` remains usable before GitHub setup: it reports the ten most recent ASC builds without raw payloads and explicitly lists missing runner variable names. Runner action dependencies are pinned to commit SHAs and checked by the offline Python policy tests. A project's local identity/build inventory can be verified against live Apple data without dispatch; local configuration and verification reports remain gitignored.

- `lib/release-ios.ts` provides pure validation/planning and refuses non-integer ASC build numbering, branch/PR refs, duplicate bundles and unsupported frameworks. `listAscBuilds` in the ASC connector paginates all app builds, preserving each resource in `rawJson`; numbers are conservatively increasing across all versions. The CLI checks ASC app identity against the first bundle and requires `appStoreTrackId` to equal `iosReleaseConfig.appId`.
- Project metadata uses one optional JSON column `iosReleaseConfig` (remote repository, ASC app ID, Team ID, ordered bundle IDs, framework and optional working directory) rather than many unrelated optional columns. `project:update --ios-config <json>` validates it; no credential belongs in this object. Migration `0014` is additive. Existing Windows `flutterProjectPath` is not used for remote builds.
- `scripts/release.ts ios|ios-status` delegates to `scripts/release-ios.ts`; Android behavior stays unchanged. iOS requires `--slug` or `--path` plus explicit `--sha --build-name`, defaults to read-only preflight without history; `--build --unsigned` dispatches an unsigned compile, `--build` dispatches a signed IPA, `--apply` dispatches TestFlight only. Capacitor and bounded path-based inference are supported. Store opening still applies pending migrations, so back up before first use of the new schema.
- `lib/connectors/github-actions.ts` scopes requests to the configured runner, verifies it is private and dispatches with `return_run_details`. A UUID correlates workflow titles and append-only `connectorRuns` (`source=ios_release`). Intent is logged before POST; acceptance is `stats.state=dispatch_accepted`, not upload success. Timeout/failure is deliberately ambiguous, without retry. `ios-status` prints the latest 100 workflow runs filtered by slug plus the live paginated ASC build inventory; it does not yet reconcile terminal job states into stored history. Run cancellation and Apple processing must be checked explicitly.
- `integrations/ios-release-runner/` is a bootstrap package for a separate PRIVATE GitHub repository, not an active workflow in this public repo. It checks its default branch, enabled app identity, exact approved SHA, input formats, framework, Xcode/Flutter pins, targets and safe relative checkout directory before app execution. The example app is disabled in the template. CI uses an ephemeral keychain and Match readonly; Apple/Match secrets are available only to the signed step. App build scripts still execute with those secrets: only reviewed source commits are allowed. Unsigned mode exposes no Apple signing secrets.
- The central Fastfile preserves native source/Podfile.lock, adjusts manual Release signing in the disposable checkout, sets push production entitlements and validates IPA main/extension identities, versions, signatures, profile expiry/type, certificate/profile match and required entitlements. Only IPA/unsigned archive and a non-secret receipt are artifacts, retained three days. TestFlight upload skips submission and processing wait; `uploaded_processing_unconfirmed` explicitly requires ASC and device verification. The package needs macOS dependency locking, Apple/Match bootstrap and an end-to-end pilot before production use. See `docs/guide/ios-release-setup-handoff.md` for exact user inputs and setup sequence.

## Android release pipeline

- **Android release pipeline** (added 2026-10-08, `lib/release.ts` + `scripts/release.ts`, guide in `docs/guide/release-workflow.md`): builds a Flutter app and publishes its AAB to a Google Play track through the Android Publisher `edits` API (`edits.bundles.upload` → `edits.tracks.update` → `edits.commit`, new `getPlayTracks`/`uploadPlayBundle` in `lib/connectors/play-console.ts`) — no Fastlane, same service account as the listing writes (needs release permission on the app in Play Console). `pnpm run release:status -- --slug <slug>` lists live tracks; `pnpm run release:android -- --slug <slug> [--path <flutter dir>] [--track internal] [--build-number <n|auto>] [--build] [--apply]` is preflight-only by default (package match, signing, version code vs highest code on Play), `--build` also runs `flutter build appbundle --release` and verifies the signature, only `--apply` uploads and commits. The intended caller is an agent working in the app's own repo: it runs the script with OpenFindability as cwd and `--path <app repo>` (no `--slug` needed — the project is matched by Gradle `applicationId` == `playConsolePackageName`); prefer `npx tsx scripts/release.ts android ...` over pnpm's `--` passthrough on Windows. New optional `Project.flutterProjectPath` (`--flutter-path` on `project:add`/`project:update`, migration `drizzle/0008_*`) stores the path so `--slug` alone is enough. Signing: if `secrets/android/<slug>/key.properties` exists (Flutter's `key.properties` format, `storeFile` relative to it) that keystore overrides the project's Gradle signing via AGP's `android.injected.signing.*` properties, otherwise the project's own config is used. Those properties are passed as `-Dorg.gradle.project.*` in `GRADLE_OPTS`, **not** as `ORG_GRADLE_PROJECT_*` env vars: verified on this machine that the env route works with `gradlew` directly but is silently dropped through `flutter build` on Windows (Dart upper-cases env var names; Gradle property names are case-sensitive). Because that failure is silent, the built AAB is always checked with `keytool -printcert -jarfile`: debug-key signer aborts, and with central signing the AAB's SHA-256 must equal the central keystore's cert or the upload aborts. `--build-number`/`--build-name` are passed to `flutter build` and never rewrite `pubspec.yaml`. `--build`/`--apply` runs are logged in `connectorRuns` with `source: "play_release"` (track/status/version/raw response in `stats`); there is no dedicated release table or dashboard section yet, and no MCP tool (not used for this flow). Android only — iOS builds need macOS.

## Project management and workflow

- Disabling a source means clearing its project mapping (for example `appStoreTrackId` or `playConsolePackageName`) while preserving metric history and connector audit logs. Add its store identifier to local `DISCOVER_IGNORE_APPS` to prevent account discovery from reconnecting it. - `docs/guide/operating-playbook.md` is a new top-level walkthrough of a full research→draft→publish session across connectors (added 2026-08-13) — the other `docs/guide/*.md` files each document one connector in isolation, this one ties them together in the actual order a session uses them, plus store-specific publish gotchas (Play Store listing writes go live in hours with no review; App Store Connect text writes need an editable draft version and still go through Apple review; App Store app name strings are globally unique across developer accounts and can 409 with `DIFFERENT_ACCOUNT`).

## Umami

- `lib/connectors/umami.ts` talks to either Umami Cloud (`https://api.umami.is/v1`, `x-umami-api-key` header) or a self-hosted instance (`UMAMI_BASE_URL` without `/v1`, `/api` prefix added, `Authorization: Bearer`). A project maps to a site through `Project.umamiWebsiteId` (`--umami` on `project:add`/`project:update`); one site per project.
- The stats payload differs by version: Cloud/v2 wraps each metric as `{ value, prev }`, self-hosted v3 returns plain numbers. `readUmamiMetric` accepts both. Reading only the wrapped shape silently stored 0 for every day against a self-hosted instance, so `umami` rows dated before 2026-08-08 are zeros and not real traffic.
- `syncUmamiProject(project, startDate, endDate)` makes one stats call per day and writes one `metricSnapshots` row per day, over the shared `backfillDays` window (default 30; `npx tsx scripts/sync.ts umami <days>` for more). It is per-day on purpose: Umami only returns unique visitors for the window requested, so daily visitors summed over a period are not unique visitors for that period.
- Tabs that export a latest state instead of a date window (via `latestPerGroup`): `OF_GscBreakdowns` (newest synced range per project, since device/country/search-appearance splits are per range, not per day), `OF_GscIndexSummary`/`OF_GscIndexIssues` (latest inspection per URL; keyed by `site_url` because unmapped properties have no project; indexed URLs appear only in the summary counts), `OF_AsoKeywords` (newest research date per project), `OF_StoreCopy` (newest App Store text per locale, without descriptions).
- `OF_AdmobBreakdown` is the per-network, per-format split of the AdMob `estimated_revenue` already in `OF_Revenue`: its rows add up to that total for the same day, they are not extra revenue.
- A GA4 property can be found without the Analytics UI: the Admin API `accountSummaries.list` with the service account lists every property it can read. Firebase projects appear there as app properties (iOS/Android/web streams in one property), and one property maps to one project through `--ga4`.
